# Owner-Approved Operating Deployment Preparation Contract

## Status and outcome

`OP-01` and `OP-02` are historical preparation/remediation evidence only. Their former `v1.0.4` candidate claim is unsupported because that tag predates stabilization and isolated-engine work; do not deploy it. TOP-01 subsequently proved the credential-free Compose lifecycle, and TOP-02 repaired the configured isolated-Codex connection path. The exact supported candidate is named only by the TOP-03 closeout after its current verification evidence is recorded. The architecture declares a separate isolated engine, dedicated profile, capability-limited read-only MCP boundary, and default-deny limited CONNECT egress proxy. The engine has no direct external network; the proxy is the only bridge to the provider-egress network and permits only exact owner-allowlisted DNS hostnames on port 443.

The outcome is a credential-free, reproducible preparation package: conditional install/start/configure/health/stop/recovery instructions, a machine-readable local preflight, and fixture evidence for local product and failure states. Preflight `ready` means that the architecture and product fixtures are ready. It is not a claim that an owner allowlist was configured, a Docker image was built, or Telegram, Codex, Claude Code, official login, provider reachability, or any live provider is operating for an owner. Those are deferred operating gates.

## Ordered owner procedure

1. **Diagnose and select:** run `python3 scripts/agentos_doctor.py --root .` from a checkout which includes the doctor. You can pass `--candidate COMMIT` to assert a specific immutable candidate. It checks only the checkout, Docker/Compose availability, loopback port, free disk, Compose configuration, and secret-free product preflight. It never starts containers, repairs state, reads credentials, or contacts external services. If `--candidate` does not match the current checkout, a `blocked` report returns a safe remediating command sequence.
2. **Configure and start, only after a ready doctor report and owner approval:** the owner must approve and set the exact provider DNS-host allowlist, then explicitly run `docker compose up -d --build`. The owner may set `AGENTOS_PORT` to select a local port; no public host, host-home mount, Docker socket mount, or credential environment variable is part of this path. A new empty runtime needs no initial archive; create a secret-free backup after personal data exists.
3. **Health and local claim, only after a successful approved start:** the owner will wait for `http://127.0.0.1:${AGENTOS_PORT:-8787}/healthz` to return `{"ok": true}`, open the local URL, claim the newly created runtime, and retain the generated local recovery material according to the UI instructions. No such operating result is recorded by this cycle.
4. **Credential and live-provider gates, only after deployment approval, owner allowlist configuration, and image build:** the owner alone chooses the isolated subscription CLI and completes its official login through the approved engine profile, then verifies provider reachability and live execution separately. If Telegram is desired, the owner separately creates a dedicated bot and enters its token into the local private connection store, then completes owner pairing. These gates are not part of preflight and no allowlist, image build, login, token, OAuth client, endpoint, live inference, or external connection is created or proven by this cycle.
5. **Stop and recover:** use `docker compose down` to stop while retaining the named data volume. Before destructive volume replacement, use `scripts/compose-backup.sh ARCHIVE.tar.gz`; stop the service, replace with an empty data volume, run `scripts/compose-restore.sh ARCHIVE.tar.gz`, then start again. Portable restore deliberately excludes credentials, sessions, local-folder grants, engine selection, and Telegram pairing, so the owner must claim and reconnect the restored runtime.

## Health, failure, and recovery contract

`/healthz` is the only unauthenticated local health endpoint. Compose must fail its health check when it cannot reach that endpoint. The preflight is fail-closed: a version mismatch, non-loopback port, missing named volume, missing non-root runtime, missing health check, missing recovery scripts, missing isolated-engine boundary, or missing limited engine-egress policy is a non-ready result with a named recovery action. A missing owner allowlist is instead a deferred operating gate because the empty policy denies every destination safely. Preflight performs no Docker operation, credential read, or external provider call. Its only network activity is a loopback fixture round trip between temporary AgentOS and engine HTTP servers.

The supported stop/recovery path preserves the named volume across `down` and refuses restore while AgentOS is running. Backup and portable restore are secret-free by contract. Interrupted or uncertain work remains in the owner-local queue and is handled through the existing recovery surface; this preparation cycle does not retry an engine or resend Telegram work.

## Threat and data boundary

The AgentOS container runs as the dedicated `agentos` user and receives only its internal `/state` owner volume. The separate engine service receives only `/engine-profile`, has no owner-state mount, host port, or direct provider-egress network, uses a read-only filesystem and read-only Codex sandbox, and communicates with AgentOS through the internal gateway and authenticated `list_notes`-only MCP callback. Its HTTP(S) proxy settings force traffic through a separate proxy that supports only `CONNECT` to exact allowlisted DNS names on port 443; missing or empty configuration denies all destinations. The proxy rejects IP literals, other methods, and other ports, bounds tunnels, and does not log request lines, headers, or tunneled bytes. The host sees one loopback AgentOS port and an owner-chosen archive directory only during backup/restore. No host home, arbitrary host directory, Docker socket, public tunnel, broad network policy, credential, or live provider payload is introduced.

The preflight report contains only version, structural readiness booleans, and recovery identifiers. It never reads owner data, private connection files, environment secrets, or external CLI credentials.

## Automated evidence and deferred operating evidence

Fixtures cover the isolated gateway/sidecar/read-only-MCP product path, version mismatch, unsafe binding, missing health check, missing runtime user, recovery behavior, the named missing-egress-policy blocker, and the default-deny limited proxy policy. Recovery fixtures still quarantine incomplete work, refuse automatic replay, preserve duplicate safety, and exclude engine profile/configuration from portable restore. The repository CI runs this suite with the existing plan/document/ledger checks and the complete test suite. Static Compose checks and fixture execution are development evidence; no owner allowlist, Docker image build, official login, provider reachability, or owner operating evidence is claimed.

Operating evidence is deliberately deferred: after OP-02 closeout and explicit owner approval, an owner can record the actual selected release, exact provider-host allowlist, Docker image build/start, local health result, official login, provider reachability/live execution, and separately configured connection health. Until then, preflight readiness remains architecture-and-fixture readiness only—neither *deployment-ready* nor *operating-configured*.

## Non-goals

OP-01 and the current remediation preparation do not configure an owner provider allowlist, install or build Docker, install a subscription CLI, enter credentials, perform official login, configure OAuth, create a Telegram bot, activate or test an external connection, run live provider inference, deploy a public endpoint, add a connector/A2A peer/marketplace capability, or change unrelated UI.
