# Continuing conversational Work from verified read progress

## Scope

Issue #1007 extends the restart boundary for a foreground Work that has a host-owned checkpoint from a supported read. The owner goal, Work identity, verified evidence, user corrections and cumulative WorkLedger remain authoritative. The owner's chosen AI decides what remains useful after reading a checkpoint. A completed read does not imply completion of the original goal. The current result judgment and delivery path still decide and record the Work outcome.

The bounded public download tool advances ranges on the host in one call and checkpoints each verified range. It returns when the file is complete or the transfer stalls, reaches a limit or needs a new decision. A paused transfer reports its verified offset and stop code. The worker can continue a resumable transfer from that offset or inspect it with a bounded preview. Routine range progress spends one tool attempt for the whole call and needs no model turns. Verified dispatch receipts use the same restart epoch and queue transaction. Their separate eligibility and authoritative-read rules are in the [recovery matrix](recovery-matrix.en.md#remaining-work-after-a-dispatch-receipt-1000). Independent async jobs and standing triggers are covered by #972.

The direct API and trusted-local subscription routes can use the tool. The subscription MCP bridge sends calls to the Still service, which holds the Work ledger, staging and redaction material. Strict isolation excludes service-relayed tools. The restricted isolated-engine profile offers only `list_notes`.

## Authority and recovery

The public-destination, pinned transport, no-secret and work-mode checks apply to every outgoing hop. The adapter starts with an anonymous GET for a single range. A bounded `200` at offset zero completes the file in one pass. If a partial first `206` has a weak or missing validator, the host discards that partial response and makes a plain GET within the same deadline. A complete response without a strong validator can be used after verification. An interrupted plain transfer has no resumable bytes. Advancing beyond offset zero requires a strong ETag, matching source identity, range and length under RFC 9110 `If-Range`. A changed source requires a new decision. Source URLs and validators remain local to the host.

A checkpoint is host-owned state tied to the Work and its active epoch. Later calls see only the committed coverage and its cumulative SHA-256 digest. Private staging accepts a host-generated reference. The transaction checks the epoch and previous revision before it publishes a durable offset. If a write outlives its transaction, the next authorized writer discards its unpublished tail. Staging uses up to 1 MiB per range, 64 MiB per Work and 256 MiB per install. A fetch has up to 60 seconds within the remaining Work budget, and each HTTP exchange retains its own deadline. When room is required, the cache can reclaim orphan staging and staged bytes from terminal Works. Portable export strips the checkpoint metadata and excludes staging.

A complete verified file appears as a downloadable Artifact on its Work in the authenticated owner interface. Still serves the exact committed bytes as an attachment. To analyze the file, the Work's own `code_run` accepts the Artifact reference and exposes only a verified read-only copy at `STILL_DOWNLOAD_FILE`. The same credential masking used for preview applies to the code input, with byte positions preserved. Preview and code output are outside data. The host confines Artifact lookup to the originating Work and rechecks the content digest before either consumer receives it.

Restart recovery atomically fences stale executions. A worker CLI ending inside the service closes its relay to further ranges, and the same Work's replacement route receives the last committed coverage as a host observation. Both paths retain the original Work identity and all prior attempt, turn and deadline accounting. A supported checkpoint and accountable read-only history are required for recovery. Owner Stop, expiry, revoked authority, pending owner actions and unknown effects still govern continuation. Work mode permits recovery and local preview, with its regular outbound checks still applied before any new fetch. The existing Plan and outcome judgment decide what remains useful.

## Verification

Use #826's production recovery and transaction fixtures, with injected HTTP and worker transports and fake clocks. Compare a resumed transfer with uninterrupted execution and verify per-range checkpointing inside one call. Test plain responses, budget limits, changed source, truncated ranges, unsafe targets and stale commits. Check that the Worker can read its own verified file through the sandbox, and that the owner can download it only within a valid session. Exercise a replacement route after a worker stop and confirm the resumed request uses the original Work and committed offset. Report model-free and model operating evidence separately.

## Reuse

Adapt the documented long-running Activity/Signal and LangGraph checkpoint patterns to existing local SQLite, WorkLedger, queue and judgment. Adopt [RFC 9110 Range and If-Range](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5), Python's HTTP and file-descriptor facilities, and the existing pinned transport. Reuse the Work artifact view, authenticated HTTP handler and the existing sandbox-runtime read allowlist and write denylist for the verified copy. The pinned runtime, license and supported platforms remain those in the [code-run design](connect-code-run-design.en.md). See #1007 for the original Existing Solutions Review.
