# 2. 온톨로지와 역할

[주제별 목차](README.md) · 개념 해설, 새 스키마나 실행 엔진의 도입 요구가 아님

## 문제: 같은 단어가 같은 사실을 뜻하지 않는다

잔액, 사용 가능한 돈, 목표를 위해 남겨둔 돈은 같은 금액을 가리킬 수도 있고 아닐 수도 있다. 요청을 받았다는 사실과 약속을 수락했다는 사실도 다르다. 이런 차이를 유지하지 못하면 AI는 유창한 문장을 만들면서도 다른 대상을 비교하거나, 미완료 의무를 이미 끝난 일로 다룰 수 있다.

[역할 기반 온톨로지 연구](../research/role-ontology-and-mandate-2026-10-05.ko.md)는 온톨로지를 개념, 관계, 의미상의 구분과 제약을 명시하는 체계로 설명한다. 핵심은 속성이 많다는 데 있지 않다. **무엇을 가리키는 정보이며, 어떤 해석을 해도 되는지 분명하게 하는 것**이다.

## 한 현실 위에 놓이는 서로 다른 구분

| 구분 | 답하는 질문 | 혼동하면 생기는 문제 |
| --- | --- | --- |
| 사실과 출처 | 누가, 언제, 무엇에 대해 말하거나 관찰했는가? | 추론이나 옛 상태를 현재 사실로 사용 |
| 도메인 의미 | 이 분야에서 대상과 관계가 무엇을 뜻하는가? | 금액·기간·범위가 다른 정보를 동일시 |
| 전문 역할 | 어떤 관점과 기준으로 문제를 보는가? | 역할 이름만 붙인 프롬프트를 전문성으로 취급 |
| 위임(Mandate) | 누구를 위해 어떤 목표를 어디까지 맡았는가? | 요청·제안·수락한 책임을 혼동 |
| 권한(Authority) | 실제로 어떤 자원과 행동이 허용되는가? | 위임받았다는 말만으로 외부 행동 실행 |
| 증거와 약속 | 무엇이 확인되었고 무엇이 아직 남았는가? | 보고했다는 사실을 완료로 취급 |

이 구분은 [Professional Roles 계약](../professional-roles-and-communication-contract.en.md)의 의미 구성과 연결된다. 역할은 허가증이 아니며 전문 자격이나 규제상 지위를 부여하지도 않는다.

## 사실을 복제하는 대신 해석을 구분한다

같은 계좌의 잔액을 일정 준비 역할은 납부 일정의 여유로, 자산관리 역할은 유동성으로 읽을 수 있다. 그렇다고 역할마다 원본 잔액을 별개의 '정답'으로 다시 만들지는 않는다. 대상·측정값·단위·시점·범위·출처를 먼저 맞추고, 그래도 값이 충돌하면 충돌 자체를 남긴다. 역할의 해석은 원사실을 덮어쓰지 않는다. 이는 [아키텍처](../personal-agentos-architecture.en.md)가 제시하는 설계 원칙이며 금융서비스의 구현 선언이 아니다.

약속도 같은 방식으로 이해할 수 있다. '금요일까지 보내 달라'는 요청, '그렇게 하겠다'는 수락, 실제 발송, 상대방의 수신 확인은 서로 다른 기록이다. 이 관계를 연결해야 무엇이 아직 남았는지 물을 수 있다. 단순히 메일에 `deadline` 필드를 붙이는 것과는 문제의 초점이 다르다.

## 온톨로지·판단·Presence의 관계

**온톨로지는 무엇을 이해하는지, 판단은 무엇을 할지, Presence는 함께 일하는 관계를 어떻게 유지하는지**를 다룬다. 전문 역할은 이 세 차원에 관점을 제공하며 별도의 말하는 인격이 아니다. 역할별 수행 지식과 보고 기준은 스킬 콘텐츠로 제공할 수 있지만, Still 핵심 코드에 '금융이면 이 순서'와 같은 분기를 추가하라는 뜻은 아니다.

의미를 표현하는 것과 실행을 강제하는 것도 다르다. '승인 전 실행 금지'라는 관계를 문서나 그래프에 적는 것만으로 실제 호출이 차단되지는 않는다. 집행은 현재의 권한·승인·실행 경계가 담당한다.

## 형식화는 목적이 아니라 선택이다

자연어 정의와 관계부터 시작할 수 있다. 그래프 데이터베이스나 형식 추론 엔진을 도입해야만 이 구분을 사용할 수 있는 것은 아니다. 반대로 개념 목록이 생겼다고 완성된 형식 온톨로지를 구현했다고 부르지도 않는다. [재사용·적용 대장](../research/role-ontology-reuse-2026-10-05.ko.md)은 개념 채택, 현재 코드와의 연결 설계, 실제 구현 도입을 구분한다.

## 남아 있는 질문

어떤 의미 구조가 실제로 대상 혼동과 권한 오해를 줄이는지 확인해야 한다. 더 많은 분류와 관계를 유지하는 비용이 도움보다 클 수도 있다. 여러 역할의 판단이 충돌할 때 하나의 그럴듯한 답으로 섞을 것이 아니라, 근거와 충돌을 어떻게 사용자에게 전달할지도 남아 있다.
