# 1. 소유와 연속성

[주제별 목차](README.md) · 개념 해설, 구현 계약이 아님

## 문제: 두뇌를 바꾸면 왜 비서까지 잃어야 하는가

Still의 출발점은 가장 좋은 모델을 직접 소유한다는 가정이 아니다. 모델을 빌려 쓰더라도, 그 모델과 함께 쌓은 사용자 이해와 진행 중인 일까지 공급자에게 묶여 있어야 하는지를 묻는다. [VISION](../VISION.md)과 [총람](../whitepapers/personal-agentos-compendium.ko.md)은 이를 한 사람을 위한 지속적인 에이전트의 문제로 다룬다.

그래서 제품의 중심은 '어떤 AI를 연결했는가'보다 **'AI를 바꾼 뒤에도 어떤 일을 이어갈 수 있는가'**다. 대화 기록을 복사하는 것만으로는 충분하지 않다. 무엇이 현재의 선호인지, 어떤 작업이 승인 대기인지, 이미 일어난 효과가 무엇인지, 다시 시도하면 안 되는 요청이 무엇인지도 남아야 한다.

## 남는 상태와 교체되는 실행 수단

| 사용자에게 남아야 하는 것 | 교체할 수 있어야 하는 것 |
| --- | --- |
| 출처와 시간, 정정 이력이 있는 기억과 맥락 | 추론·생성을 수행하는 모델 |
| 목표, 진행 중인 일, 다음 단계와 미완료 의무 | 구독 CLI, 모델 API, 위임 실행기 |
| 권한, 승인과 취소 상태 | 도구·연결·스킬 공급자 |
| 결과물과 무엇이 실제로 일어났는지에 대한 기록 | 일을 수행하는 개별 에이전트 |

[아키텍처](../personal-agentos-architecture.en.md)의 Owner·Context·Memory·Work·Grant·Artifact·Evidence는 이러한 책임을 구분한다. 이것은 각각 새로운 저장소를 만들라는 요구가 아니다. 서로 다른 의미를 하나의 대화 로그나 모델 내부 상태로 뭉개지 말자는 구분이다.

예를 들어 다른 AI로 바꾼 뒤 '아까 준비한 것에서 수량만 바꿔줘'라고 요청했다고 하자. 앞의 대상과 준비 상태는 이어갈 수 있어야 한다. 그러나 이전 승인까지 변경된 수량에 자동 적용할 수는 없다. **연속성은 권한을 그대로 복제하는 기능이 아니다.** 이 사례는 설계 설명이며 모든 실행 경로에서 관찰된 기능을 뜻하지 않는다.

## 소유는 저장 위치만으로 결정되지 않는다

로컬에 파일이 있다는 사실과 사용자가 통제할 수 있다는 사실은 다르다. 무엇이 저장되어 있는지 볼 수 있고, 잘못된 이해를 고치며, 접근을 중단하고, 결과를 보존한 채 실행 수단을 교체할 수 있어야 한다. [Owner Control](../owner-control-contract.en.md)은 이러한 권리를 관찰 가능한 요구사항으로 다룬다.

반대로 로컬 설치라고 해서 모든 추론이 로컬에서 일어나는 것은 아니다. 외부 AI를 선택하면 그 요청에 사용되는 맥락이 외부로 전달될 수 있다. 원격 서비스의 내부 보관·삭제까지 Still이 직접 통제하는 것도 아니다. 소유를 설명할 때는 데이터 위치, 실제 제어 범위, 원격 시스템의 한계를 함께 말해야 한다.

데이터를 내보내는 것, 의미를 유지하는 것, 새 실행기에서도 업무를 이어가는 것은 서로 다른 수준이다. 내보내기 파일이 있다는 이유만으로 세 수준이 모두 해결되었다고 판단하지 않는다.

## 한 사람을 중심으로, 여러 역할을 사용한다

'개인'은 서비스를 받는 중심을 뜻하고, '비서'는 그 사람을 돕는 역할 중 하나다. 연구·구매·프로젝트 등으로 역할이 확장되어도 사용자마다 별개의 사실과 권한을 무질서하게 복제하는 구조는 피한다. 역할의 차이는 [온톨로지와 역할](ontology-and-roles.ko.md)에서, 관계가 이어지는 경험은 [Presence](presence-and-collaboration.ko.md)에서 다룬다.

## 남아 있는 질문

모델이 바뀌어도 같은 기록을 읽는다는 것과 같은 품질의 판단을 한다는 것은 다르다. 의미 이전의 손실, 도구 능력 차이, 인증 재연결과 미완료 작업의 복구를 실제로 확인해야 한다. 사용자에게 통제 수단을 제공하면서도 그 사람이 시스템 운영자가 되지 않게 하는 것 역시 해결해야 할 긴장이다.
