# 6. 권한과 증거

[주제별 목차](README.md) · [이전: Presence와 협업](presence-and-collaboration.ko.md) · [다음: 생태계와 사업 가설](ecosystem-and-business.ko.md)

## 이해, 허용, 실행, 완료는 다른 사실이다

AI가 요청을 이해해도 실행 권한이 없을 수 있다. 권한이 있어 호출했더라도 실패할 수 있다. 외부 서비스가 처리한 뒤 응답만 끊겼다면, 실패로 단정하고 재시도하는 것이 오히려 중복 실행을 만들 수 있다.

Still은 요청의 의미를 판단하는 일과 실제 권한·실행 결과를 확인하는 일을 구분한다. 모델의 확신이나 매끄러운 설명은 실행 사실을 대신하지 않는다. 이 책임은 [사용자 통제 기준](../owner-control-contract.en.md), [실행 기준](../assistant-execution-contract.en.md), [연결·위임 기준](../connection-delegation-contract.en.md)에 정의되어 있다.

## 정책을 표현하는 일과 집행하는 일

ODRL 2.2는 자원에 대한 허용·금지·의무와 조건을 표현하는 정보 모델을 제공한다. 이는 “어떤 행동이 어떤 조건에서 허용되는가”를 명시할 때 비교할 수 있는 표준이다. 그러나 ODRL로 정책을 표현했다는 사실만으로 Still의 실행 경로가 그 정책을 집행한다고 결론지을 수는 없다. 표현의 적합성과 구현의 집행 여부는 별도로 확인할 문제다. [R11](references.md#r11)

Still에서도 역할은 판단 관점을, 맡긴 일의 범위는 목표와 책임을 설명한다. 실제 접근과 행동은 현재 권한(Grant)과 적용되는 승인 규칙에 따라야 한다. 설치·연결·로그인 또는 신뢰 등급이 모든 행동을 허용하는 것은 아니다.

외부 행동은 읽기, 장바구니 변경, 개인정보 입력, 메시지 전송, 예약 제출, 결제 등으로 구분한다. 대상·수량·금액이 바뀌면 이전 승인이 새 행동까지 허용하는지도 확인해야 한다. 다만 모든 행동에 동일한 사전 확인을 요구한다는 설명은 현재 파일럿 정책과 다르다.

파일럿에서는 일부 민감도 판단과 검색 분리 제약을 제거했지만, 폴더 접근 범위, 비밀정보 보호, 건별 결제 승인, 확인되지 않은 외부 변경의 재실행 방지 같은 경계는 유지한다. 과거의 더 강한 제약이나 장기 설계를 현재 집행되는 규칙처럼 소개하지 않는다. 적용 범위는 [기억·사용자 모델 기준 문서](../secretary-agency-contract.en.md)의 현행 파일럿 규칙을 따른다.

## 출처 기록이 있다는 것과 사실이라는 것은 다르다

W3C PROV-AQ는 출처 기록 자체의 정확성이나 권위가 보장되지 않으며, 그 기록을 신뢰할지는 별도로 판단해야 한다고 설명한다. 기록의 계보를 추적할 수 있다는 것과 내용이 참이라는 것은 다른 주장이다. [R12](references.md#r12)

Still의 실행 기록(Evidence)도 그 기록이 뒷받침하는 범위 안에서 읽어야 한다. 예를 들어 전송 요청의 호출 기록, 서비스의 접수 응답, 실제 발송 확인, 상대방의 수신 확인은 각각 다른 주장에 답한다. “호출했다”는 기록만으로 “상대방이 받았다”고 말할 수는 없다.

| 보고할 사실 | 필요한 구분 |
| --- | --- |
| 요청·계획 | 무엇을 하려는지 정했다. |
| 실행 시도 | 해당 실행 경로를 호출했다. |
| 관찰 | 서비스 응답이나 화면 등에서 특정 상태를 확인했다. |
| 확인된 완료 | 요청한 결과가 이루어졌다고 말할 근거가 있다. |
| 부분 완료 | 확인된 결과와 아직 완료하지 못한 부분이 나뉜다. |
| 실패 | 요청한 결과가 이루어지지 않았다는 근거가 있다. |
| 미확인 | 외부에서 어떤 결과가 발생했는지 확정할 수 없다. |

이 표는 설명을 위한 구분이며 새로운 Work 상태 목록이 아니다. 취소 역시 새 호출 차단, 실행 중단, 이미 발생한 변경의 되돌리기를 나누어 설명해야 한다.

## 검증 자료는 서로 다른 질문에 답한다

증거를 하나의 점수나 순위로만 정리하면 중요한 차이가 사라진다. 단위 테스트는 실제 서비스에서 보기 어려운 거부 조건을 반복 확인할 수 있지만, 실계정의 전체 경험을 보여 주지는 않는다. 실사용 한 번은 그 상황을 관찰한 근거지만 모든 조건에서의 재현성을 보장하지 않는다.

| 자료 | 확인할 수 있는 범위 | 그것만으로 알 수 없는 것 |
| --- | --- | --- |
| 기준 문서·스키마 | 의도한 규칙과 데이터 형식 | 구현과 실제 집행 여부 |
| 단위·통합·모의 환경 테스트 | 정해진 조건에서의 처리와 거부·복구 | 실제 외부 서비스의 현재 동작 |
| 설치 점검 | 특정 배포본의 설치와 실행 | 전체 업무의 실계정 완료 |
| 실사용 관찰 | 특정 환경·시점·요청의 경험과 결과 | 다른 환경의 재현성이나 일반 정확도 |

[제품 현황](../product-status.en.md)과 [릴리스 기록](../release-manifest.json)은 이 차이를 확인하는 진입점이다. 데모 화면이나 AI의 성공 응답만으로 외부 계정의 최종 상태까지 검증했다고 하지 않는다.

## 투명성과 비밀정보 보호를 함께 유지한다

사용자는 어떤 정보가 쓰였고 어디로 전달되었으며 무엇이 바뀌었는지 확인할 수 있어야 한다. 이를 위해 비밀정보나 제한 없는 도구 입력·출력을 로그와 공개 저장소에 남길 필요는 없다. 필요한 출처·대상·시점·결과를 기록하면서 열람과 보관 범위를 제한한다.

남은 문제는 승인 부담과 통제권, 결과 확인 비용과 유용성 사이의 균형이다. 이를 설명할 때는 실제로 막는 규칙과 AI에게 따르도록 요청한 지침을 구분해야 한다. 사용자에게 강제되는 보호장치로 소개할 수 있는 것은 실제 실행 경로에서 확인한 범위다.
