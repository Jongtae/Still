# 6. 권한과 증거

[주제별 목차](README.md) · 개념 해설; 정책의 적용 범위는 현재 계약이 정함

## 문제: 이해했다, 허용됐다, 실행됐다, 끝났다는 서로 다른 말이다

AI가 요청을 이해하고 그럴듯한 결과를 설명할 수 있어도 실제 행동은 허용되지 않았거나 실패했을 수 있다. 반대로 외부 요청이 전달된 뒤 응답만 끊겼다면 실패했다고 단정해 다시 실행하는 것이 위험할 수 있다.

Still은 의미 판단과 함께 **현재 권한과 관찰된 효과를 별도로 유지하는 구조**를 지향한다. 말의 설득력이나 모델의 확신이 실행 사실을 대신하지 않는다. 이 경계는 [Owner Control](../owner-control-contract.en.md), [Execution](../assistant-execution-contract.en.md), [Connection and Delegation](../connection-delegation-contract.en.md)에 나뉘어 정의되어 있다.

## 맡긴 일과 실행 권한은 같지 않다

역할은 어떤 기준으로 판단할지를, 위임은 어떤 일을 맡았는지를 설명한다. 실제 접근과 행동의 허용 범위는 Grant와 적용되는 승인 경계가 정한다. 설치, 연결, 로그인, 신뢰 등급도 모든 행동에 대한 승인을 만들지 않는다.

외부 효과 역시 구분해야 한다. 읽기, 장바구니 변경, 개인 정보 입력, 메시지 전송, 예약 제출, 결제는 같은 행동이 아니다. 수량·대상·금액이 달라지면 이전 승인이 새 행동을 포괄하는지도 다시 확인해야 한다. 다만 **모든 효과가 현재 파일럿에서 똑같이 사전 확인을 요구한다는 뜻은 아니다.** 정확한 정책은 현재 계약과 파일럿 보완을 따라야 한다.

특히 기존 파일럿은 비밀 보호와 건별 결제 승인을 유지하면서 일부 과거의 민감도·검색 분리 게이트를 제거했다. 따라서 과거의 강한 통제 설명을 새 본문에 복사하여 오늘도 집행되는 것으로 표현하면 안 된다. 현재의 정보 사용 감사와 남아 있는 경계는 [Secretary Agency](../secretary-agency-contract.en.md)의 현재 규칙을 확인한다.

## 결과를 정확하게 표현한다

| 구분 | 의미 |
| --- | --- |
| 요청·계획 | 하려는 행동과 목표가 정해짐 |
| 시도 | 실행 경로가 호출됨 |
| 관찰 | 해당 경로가 반환하거나 보여 준 상태가 있음 |
| 확인된 완료 | 요구한 결과를 주장할 수 있는 근거가 있음 |
| 부분 완료 | 일부 결과만 확인됨 |
| 실패 | 완료되지 않았다는 근거가 있음 |
| 미확인 | 외부 효과를 확정할 수 없음 |

이 표는 Work 상태 enum을 새로 정의하는 것이 아니라 보고할 때 구별해야 할 사실을 설명한다. 예를 들어 '보내기 요청을 호출했다'와 '상대방이 받았다'는 다른 증거를 필요로 한다. 어떤 주장을 하는지에 맞는 증거가 있어야 한다.

취소도 새 호출을 막는 것, 로컬 실행을 멈추는 것, 이미 일어난 외부 효과를 되돌리는 것이 서로 다르다. 확인하지 못한 원격 취소나 삭제를 완료했다고 말하지 않는다.

## 기능 근거에도 등급이 있다

계약은 무엇을 지켜야 하는지 정의한다. 스키마는 형식, 단위·fixture 테스트는 특정 조건의 경로, 설치 점검은 특정 빌드의 설치와 실행을 확인한다. 실사용 기록은 그 환경과 시점에서 관찰된 경험이다. 한 등급의 근거가 다른 등급으로 자동 승격되지는 않는다.

[제품 현황](../product-status.en.md)과 [release manifest](../release-manifest.json)는 이 구분을 적용하는 진입점이다. 데모 화면이나 모델의 성공 응답만으로 외부 계정의 최종 상태까지 독립 검증했다고 할 수 없다. 오프라인 기억 실험도 실서비스 전체의 정확도와 동일한 지표가 아니다.

## 투명성은 모든 원문을 공개하는 것이 아니다

사용자는 무엇을 사용했고 어디에 보냈으며 어떤 결과가 남았는지 알 수 있어야 한다. 그러나 이를 위해 비밀, 제한 없는 도구 payload, 사적인 원문을 로그나 공개 저장소에 남길 필요는 없다. 필요한 출처·시점·대상·결과를 보존하면서 공개와 보관의 범위를 제한해야 한다.

## 남아 있는 질문

사용자에게 지나친 승인 부담을 주지 않으면서 실제 통제권을 어떻게 유지할 것인가? 연결한 외부 실행기가 어떤 부분을 자체 처리할 때 통제의 한계를 어떻게 설명할 것인가? 결과 확인 비용이 큰 작업에서 미확인 상태와 유용한 부분 결과를 어떻게 함께 전달할 것인가?
