# 4. 판단과 실행

[주제별 목차](README.md) · [이전: 기억과 학습](memory-and-learning.ko.md) · [다음: Presence와 협업](presence-and-collaboration.ko.md)

## 요청마다 별도의 프로그램을 만들지 않는다

사용자는 기능 이름이나 정해진 문장만으로 부탁하지 않는다. 표현이 달라질 때마다 핵심 코드에 처리 절차를 추가하면 새로운 상황을 기존 시나리오에 억지로 맞추게 된다. 그렇다고 권한 확인과 실행 결과까지 모두 모델의 추측에 맡길 수는 없다.

Still의 [개발 원칙 C16](../development-constitution.en.md)은 의미를 이해하고 일을 수행하는 능력을 AI에 맡기되, 상태·권한·비밀정보·결제 승인·예산과 같은 경계는 시스템이 유지하도록 구분한다. 분야별 수행 지식은 AI가 선택해 읽는 스킬 콘텐츠로 제공하고, 특정 요청의 답을 핵심 코드에 고정하지 않는 방향이다.

## 생각하고 실행한 뒤 관찰하는 과정

ReAct는 추론과 행동을 번갈아 수행하면서 환경에서 얻은 관찰을 다음 판단에 활용하는 접근이다. Still의 설계와 비교할 지점은 한 번 세운 계획을 끝까지 밀어붙이기보다 실행 결과에 따라 계획을 수정한다는 점이다. [R7](references.md#r7)

그러나 ReAct의 결과가 Still의 판단 모델과 실행 AI를 분리한 구조가 더 우수하다는 증거는 아니다. 별도 판단이 오류를 줄이는지, 지연과 비용만 늘리는지는 Still의 조건에서 비교해야 한다. 또한 연구의 추론 기록을 사용자에게 숨은 추론 과정이나 원시 프롬프트를 공개해야 한다는 요구로 옮기지 않는다. 사용자에게 필요한 것은 실행 사실, 근거, 한계와 다음 선택이다.

## 판단과 권한 집행의 책임

| 책임 | 다루는 질문 |
| --- | --- |
| 의미 판단 | 무엇을 요청했고, 어떤 맥락과 다음 행동이 적절한가? |
| 권한 집행 | 이 자원에 대한 이 행동이 현재 범위 안에서 허용되는가? |
| 실행 | 선택된 AI와 도구가 실제로 무엇을 시도했는가? |
| 결과 평가 | 목표가 충족되었는가? 확인된 결과와 미확인 결과는 무엇인가? |

[판단 기준 문서](../decision-layer.en.md)는 작업 조정과 의미 판단을, [실행 기준 문서](../assistant-execution-contract.en.md)는 실행·복구·결과 확인을 다룬다. 모델이 목표를 달성했다고 판단해도 외부 서비스의 변경이 확인되지 않았다면 완료로 보고할 수 없다. 현재 권한, 승인한 대상과 조건, 중복 실행 방지는 별도로 확인한다.

계획은 수정 가능한 지시서다. 사용자가 도중에 조건을 바꾸면 실행 AI뿐 아니라 이후의 계획과 결과 평가에도 수정이 전달되어야 한다. 반영할 수 없는 실행 경로나 이미 끝난 행동에는 그 한계를 밝혀야 한다. 결과를 알 수 없는 외부 행동을 다시 실행하는 것은 일반적인 재계획과 다르다.

## 연결 규격은 업무 능력의 보증이 아니다

MCP의 2025-06-18 아키텍처 문서는 호스트, 클라이언트, 서버의 책임을 나눈다. 호스트는 연결과 사용자 동의를 관리하고, 서버는 도구·자원·프롬프트를 제공한다. 이는 여러 도구를 일관되게 연결하는 설계의 참고점이다. [R8](references.md#r8)

Still에서는 이 구분을 실제 실행 경로와 대조해야 한다. 도구 목록에 보이는 것, 호출할 수 있는 것, 사용자 권한 안에서 동작하는 것, 원하는 결과를 내는 것은 각각 확인할 사항이다. MCP의 기능 협상도 프로토콜 지원 여부를 나타내며, 도메인 전문성이나 작업 성공을 인증하지 않는다.

스킬 역시 수행 지식이지 권한이 아니다. 조사 방법이나 보고 기준을 스킬로 제공할 수 있지만, 스킬을 읽었다는 이유로 서비스 접근이나 결제가 허용되지는 않는다. 외부 실행기가 자체 처리하는 부분과 Still이 통제하는 부분은 [연결·위임 기준](../connection-delegation-contract.en.md)에 따라 구분한다.

## 추가 판단의 가치는 비교로 확인한다

더 많은 판단 단계가 항상 더 좋은 결과를 만드는 것은 아니다. 반대로 호출을 줄였다는 이유만으로 경험이 개선되었다고 할 수도 없다. 같은 요청과 권한 조건에서 유효한 첫 응답 시간, 정정 반영, 최종 결과의 정확성, 재시도 비용을 함께 비교하는 편이 타당하다.

이 장의 질문은 “모델을 몇 번 호출할 것인가”보다 “어떤 판단이 실제 오류를 막거나 일을 끝내는 데 도움이 되는가”다. 빠른 답변과 정확한 결과 확인의 균형은 설계 구호가 아니라 관찰할 대상으로 남는다.
