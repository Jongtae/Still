스킬과 전문성

스킬은 AI가 작업 방법을 불러 쓰는 내용 묶음입니다. 이 페이지는 스킬이라는 형식과 거래 가능한 수행 능력의 차이, 스킬 공급 원칙, 인터페이스 결정, 첫 실사용 표본이 말해 주는 것과 말해 주지 않는 것, 패키지와 외부 프로젝트와의 관계를 정리합니다.

원고: 백서 8–9장, 총람 12장. 최종 갱신 2026년 10월 14일.

형식과 수행 능력은 다릅니다

근거 가설. 백서 8장, 총람 12.1절

공개된 Agent Skills 형식은 지침이 담긴 SKILL.md 파일에 스크립트, 참고 자료, 템플릿을 선택적으로 묶습니다. 전문 지식과 작업 절차를 나눠 주는 단위입니다. 하지만 백서는 배포할 수 있는 형식과 거래할 수 있는 수행 능력을 구분합니다. 작업 방법이 적힌 파일을 주는 일, 특정 환경에서 동작하도록 유지하는 일, 결과 품질을 확인하는 일, 실패를 지원하는 일은 서로 다른 상품입니다.

‘영수증 정리 스킬’이라는 이름만으로는 사는 사람이 무엇을 받는지 알기 어렵습니다. 어떤 입력을 다루는지, 어떤 도구가 필요한지, 어떤 모델과 환경에서 시험했는지, 중복과 누락을 어떻게 확인하는지, 서비스가 바뀌면 누가 고치는지가 함께 드러나야 합니다.

스킬 경제의 목적은 모든 서비스를 Agent라는 이름으로 바꾸는 것이 아니라, 전문 수행 능력을 발견하고 위임하고 검증할 수 있게 만드는 것이다.

백서 8장

스킬 시장도 새 종속을 만들 수 있습니다. 파일 형식이 공개돼 있어도 필수 실행 환경, 평판, 결제, 사용자 맥락 접근이 한 사업자에게 묶이면 경쟁은 제한됩니다. 모든 스킬이 스스로 추론하는 Agent일 필요도 없습니다. 안정된 절차를 실행하는 소프트웨어나 사람이 검토하는 전문 서비스가 더 맞을 수 있습니다. 실행 증빙은 수행 능력을 확인하는 근거의 일부일 수 있지만, 증빙을 발급했다는 사실이 품질 보증이나 사용자 만족의 증명은 아닙니다.

먼저 받아 쓰고, 맞추고, 빈틈만 배웁니다

근거 계약. 총람 12.2절

2026년 10월 1일 소유자는 같은 일을 반복할 때마다 AI가 특정 사이트의 작동 방식을 시행착오로 다시 알아내야 할 이유가 없다고 말했습니다. 누군가 이미 만들어 두었거나 서비스가 직접 내놓은 스킬이 있을 수 있다는 것입니다. 스킬 공급 프로그램의 원칙은 먼저 공급받고, 다음에 맞추고, 빈틈만 학습한다였습니다.

요구사항 14개는 이 프로젝트의 사고방식을 압축합니다. 사용자별 학습보다 공급이 먼저입니다. 찾는 범위는 한정하고 결과는 재사용합니다. 스킬 가져오기, 도구 연결, 작업 위임은 서로 다른 통합 방식입니다. 스킬의 허용 도구 표시는 아무 권한도 주지 않습니다. 방법은 재사용하되 사실은 다시 읽습니다. 다시 실행하기 전에 현재 상태와 맞춥니다. 지식은 권한이 아니므로 공개 스킬을 가족과 나눈다고 계정이나 기록을 나누는 것이 아닙니다. 한 번 성공한 기록이 자동으로 믿을 만한 스킬이 되지는 않습니다. 새 기능은 기존 동작을 그대로 둡니다.

소유자는 이미 잘 되던 장바구니 같은 동작을 보존하라고 했고, 큰 재설계를 토큰이 많이 드는 시험으로 보완하지 말라고 했습니다. 그래서 프로그램은 다시 짓기가 아니라 인터페이스를 먼저 정하고 시험을 한정하는 방향으로 다시 짜였습니다.

인터페이스 결정

근거 계약·구현. 총람 12.3절

결정 기록은 스킬을 이렇게 정의했습니다. 스킬은 이미 있는 AgentPackage가 싣고 오는, 선택적이고 버전이 있는 지식입니다. 새로운 실행기도, 새로운 권한도 아닙니다. 작업을 맡은 AI는 부작용 없는 두 가지 호스트 동작(skill_load, skill_resource)으로 내용에 접근합니다. 두 동작은 한곳에 정의되어 있어 API 직접 호출, Codex, Claude Code 경로가 똑같이 받습니다. 다른 형식의 스킬은 가져올 때 한 번 정규화합니다. 스킬을 끄면 도구 목록이 스킬이 생기기 전과 바이트 단위로 같도록 단계적으로 바꿨습니다. 사이트별 전략 클래스, 사이트 상속 구조, 의무적인 전문가 연쇄, 번역 에이전트, 스킬 전용 검증기는 채택하지 않았습니다.

재사용 검토는 정확한 개정과 함께 남았습니다.

표 1. 스킬 인터페이스의 재사용 검토
후보결정이유
Agent Skills 명세채택형식과 단계적 공개 방식. Still의 실행 메타데이터는 그 밖에 둡니다
skills-ref실행 의존으로는 거절스스로 ‘알파, 운영용 아님’이라고 밝힙니다. 시험에서 적합성 기준으로만 씁니다
Microsoft Agent Framework SkillsProvider의미만 맞춤경로 포함·심볼릭 링크 규칙은 따르되, 자체 에이전트 루프와 승인 계층은 Still의 권한과 겹칩니다
PyYAML채택중복 키를 거부하는 SafeLoader 하위 클래스로만 씁니다. 이 기능이 더한 유일한 의존입니다
python-frontmatter거절필요한 계약을 더하지 못하고 중복 키를 조용히 받습니다
skills.sh CLI, Hermes Skills Hub관례만 맞춤출처 명세 형태, 압축 파일 상한, 격리, 신뢰 단계. CLI 자체는 쓰지 않고, 해시와 정규식 검사는 안전의 증명이 아닙니다

자료: 『Still 총람』 v0.1, 12.3절. 원표 재수록.

예산도 기존 작업 예산 안에 두었습니다. 목록은 최대 32개 항목과 8 KB, 작업 하나당 스킬 불러오기 3회와 자료 읽기 8회 같은 식입니다. 첫 외부 공급원은 특정 커밋에 고정한 공개 저장소 하나였고, 라이선스 파일이 Apache-2.0인 폴더만 받았습니다. 라이선스 파일이 없으면 ‘라이선스 불명’으로 표시했고, 소스는 볼 수 있지만 오픈소스가 아닌 스킬은 뺐습니다.

AI 명령줄 도구가 소유자의 홈 폴더에 있는 검토되지 않은 스킬을 작업 AI에게 조용히 보여 주는 위험도 찾아 막았습니다. Codex에는 스킬 지침 포함을 끄는 설정을, Claude Code에는 슬래시 명령을 끄는 플래그를 넘깁니다. 실제 codex와 가짜 모델, 미끼 스킬로 확인했습니다.

주의 ‘구현’은 코드와 단위·통합 시험으로 확인했다는 뜻입니다. 실제 계정과 실제 서비스에서 스킬이 잘 동작한다는 뜻이 아닙니다.

첫 실사용 표본과 주장의 범위

근거 관찰·구현. 총람 12.4절

스킬 평가는 ‘두 번째 시험 프로젝트가 아니다’라는 말로 시작합니다. 이미 있는 증거를 목록에 대응시키고, 정말 빠진 확인만 더하고, 아직 증명되지 않은 것을 적습니다. 소유자가 승인한 실사용 표본 계획은 실제 Codex와 로그인한 브라우저로 사례 네 개를 차례로 돌리고, 제품 줄 하나만 바꾸고, 결제는 하지 않고, 작업·턴·도구 시도·시간에 상한을 두고, 거짓 완료나 요청하지 않은 효과가 처음 나오면 멈추고, 끝나면 원래 상태로 되돌리는 것이었습니다.

10월 3일의 첫 실행은 첫 사례에서 멈췄습니다. 브라우저가 로그아웃된 상태였고 AI는 장바구니를 건드리지 않은 채 바로 로그인을 요청했습니다. 그리고 진실성 버그가 하나 드러났습니다. 그 작업이 ‘성공’으로 기록된 것입니다. 요청에 없던 계정 소유자를 추정한 답도 함께 기록됐습니다.

그래서 주장할 수 있는 것과 없는 것이 갈립니다.

표 2. 스킬에 관해 확인된 것과 주장하지 않는 것
구분내용
확인된 것모의 자료, 실제 브리지 프로세스 하나, 실제 공개 스킬 설치 하나로 공급, 고정, 회수, 경로 동등성, 꺼진 경로의 보존을 확인했습니다
주장하지 않는 것실제 사이트의 장바구니 성공률, 모델이 방법을 얼마나 따르는지, 대화 품질, 토큰이나 시간 절감
확인되지 않은 전제‘누군가 이미 해당 마트의 스킬을 만들어 두었다’는 공급 전제. 공개 쇼핑 스킬 후보 세 개는 Playwright 스크립트, 해외 마트 하나를 위한 주입 JavaScript, 자체 MCP 서버가 필요해 거절했습니다

자료: 『Still 총람』 v0.1, 12.4절을 요약한 표. 새 수치는 없습니다.

외부 스킬을 가져오는 증거와 사이트 지식 내용의 증거는 별개이며, 더 강한 하나의 주장으로 합치지 않았습니다.

AgentPackage와 배포 플랫폼

근거 계약. 총람 12.5절

주의 이 절은 규칙과 설계입니다. 아무 외부 패키지나 실행하는 기능도, 공개 마켓플레이스도 지금 되는 것으로 주장하지 않습니다(지금 주장하지 않는 것).

장기적으로 소유자는 더 나은 에이전트를 앱처럼 설치하고 바꿀 수 있어야 합니다. 생애주기는 찾기 → 살펴보고 내려받기 → 검증 → 단계 배치 → 상태 점검 → 꺼진 채로 설치 → 권한 부여·활성화·연결을 따로 → 작업 범위 권한으로 실행 → 업데이트나 되돌리기 → 비활성화나 격리 → 제거로 이어집니다. 권한, 데이터 목적지, 기억이나 백그라운드 동작, 의존성, 예산, 결과가 큰 행동을 넓히는 업데이트는 새 권한이 필요합니다. 업데이트가 실패하면 알려진 정상 상태로 돌아가는 길이 정의됩니다. 제거는 패키지의 권한을 없애지만 소유자의 산출물과 보존된 증거는 지우지 않습니다. 패키지 내부 기억은 정본이 아닙니다.

능력을 얻는 방식에는 L1부터 L5까지 사다리가 있습니다. 직접 설치, 추천, 소유자가 승인한 계획, 범위가 한정된 상시 획득, 커널이 중개하는 자기 요청입니다. L4와 L5는 첫 최소 제품 범위 밖입니다. 에이전트가 스스로 설치·활성화·권한 상승을 끝내는 것은 기본 동작이 아닙니다. 추천은 정보일 뿐 능력 상태를 바꾸지 않으며, 모델의 제안이나 목록 항목이나 막연한 ‘응’은 설치나 승인이 아닙니다.

외부 프로젝트와의 관계

근거 계약·구현. 총람 12.6절

재사용이 늘수록 외부 프로젝트와의 관계를 정확히 적어야 합니다. 관계 지도는 공격 표면(설치한 코드)과 실제 권한(실행 때 실제로 투영되는 것)을 나누고 둘이 서로를 함의하지 않는다고 적습니다. 관계는 참고만, 가져와 고침, 실행 패키지, 프로토콜·스키마 적합, 버전 있는 내용, 외부 서비스의 여섯 가지로 분류합니다. 예를 들어 모델 공급자는 SDK 없이 통신 규약을 직접 구현해 닿으며, 문서는 이를 ‘명시적으로 검사하지 않은 빈틈’이라고 이름 붙였습니다. 온톨로지·출처 표준(OWL 2, SKOS, SHACL, PROV-O)은 참고용일 뿐 RDF나 추론기 실행은 없습니다.

의존성 관리는 uv 잠금 파일 하나와 Dependabot을 택했습니다. Renovate는 스킬 내용의 커밋 고정을 추적할 수 있었지만, 스킬 커밋을 바꿔도 복사한 바이트, 라이선스, 해시, 로컬 래퍼, 의미 영향의 증거를 안전하게 갱신하지 못하므로 거절했습니다. 봇이 올린 변경은 ‘발견 후보이지 구현 권한이 아닙니다’. 공식 MCP SDK는 호스트의 stdio 경로에서만, 선택 추가 기능으로 맞춰 썼습니다. SDK가 끌고 오는 하위 패키지 13개가 설치 공격 표면을 늘린다고 결정문에 적었고 라이선스를 각각 확인했습니다.

상류 기여도 조심스러웠습니다. 공개 접미사 목록 패키지의 한 릴리스에서 휠과 소스 배포가 서로 다른 목록을 담는 결함을 재현하고 알려진 정상 버전으로 고정했습니다. 상류 이슈 초안은 만들었지만 제출은 소유자의 별도 승인에 맡겼습니다. MCP SDK의 응답 처리 문제는 이미 열린 상류 이슈와 겹쳐 새로 제출하지 않았고, 시험이 딸린 로컬 어댑터를 두었다가 상류 수정이 나오면 걷어내기로 했습니다.
