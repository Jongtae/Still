기억과 개인 상태

기억을 옮긴다는 것은 대화 기록을 내보내는 것보다 넓습니다. 이 페이지는 기억 이동의 세 수준, 기억과 권한의 구분, 맥락과 기억의 차이, Still의 지금 기억 정책을 설명합니다.

원고: 백서 4장, 총람 5.1·5.3·7.4·7.9절, 24장. 최종 갱신 2026년 10월 14일.

기억 이동의 세 수준

근거 제안. 백서 4.1절

백서는 기억의 이동을 세 수준으로 나눕니다.

데이터의 이동
기록을 읽을 수 있는 형식으로 가져옵니다.
의미의 이동
그 기록이 사실인지, 사용자의 선호인지, 모델이 추정한 내용인지, 나중에 수정됐는지까지 보존합니다.
사용의 연속성
새 환경이 그 정보를 알맞게 적용해, 사용자가 이미 설명하거나 정정한 내용을 반복하지 않게 합니다.

예 “평일에는 소고기를 피하고 싶다”는 선호가 “채식주의자”로 저장된다면 데이터는 이동했지만 의미는 바뀐 것입니다. 일시적인 출장 조건이 영구적인 생활 선호로 옮겨지는 경우도 같습니다.

그래서 백서는 내용과 함께 출처, 시점, 적용 범위, 사용자 확인 여부, 수정 관계, 유효 기간도 옮기자고 제안합니다. 옮기는 대상은 확인할 수 있게 저장된 정보입니다. 모델 안에만 반영된 학습 결과나 겉으로 드러나지 않는 상태까지 옮긴다는 약속은 아닙니다.

이미 있는 기능과의 차이

근거 사례. 백서 4.2절

기억 이동을 지원하는 기능은 이미 있습니다. Claude의 공식 안내는 다른 AI 공급자와 기억을 가져오고 내보내는 기능을 설명하면서, 기억 가져오기는 실험적인 기능이라 항상 성공적으로 반영되지는 않을 수 있다고 밝힙니다.

따라서 문제는 “아무도 기억을 옮기지 못한다”가 아닙니다. 백서가 요구하는 다음 단계는 무엇이 옮겨졌고, 무엇이 빠졌으며, 어떤 의미가 바뀌었는지 사용자가 확인할 수 있을 만큼의 이전 품질입니다.

기억의 이전은 권한의 복제가 아닙니다

근거 제안. 백서 4.3절

사용자가 특정 서점을 선호한다는 정보와, 그 서점 계정에서 구매할 수 있는 권한은 별개입니다. 진행 중인 구매 검토를 옮기는 것과 결제를 실행할 권한을 옮기는 것도 다릅니다. 백서가 제안하는 이전 절차는 다음과 같습니다.

  • 새 환경에서 필요한 권한을 다시 확인합니다.
  • 옮긴 결과를 가져온 항목, 제외한 항목, 서로 충돌한 항목, 확인할 수 없는 항목으로 나눠 보여 줍니다.
  • 과거 기록이 최근의 명시적인 수정과 충돌하면 과거 기록을 되살리지 않습니다. 철회되거나 수정된 기억도 되살리지 않습니다.
  • 가져온 문장은 참고 데이터이며 새 권한을 주는 명령이 아닙니다. 연결 비밀값은 기억 묶음에 넣어 옮기지 않습니다.
  • 사용자가 새 환경의 결과를 확인하기 전에 기존 자료를 자동으로 지우지 않습니다.

Portable Memory의 최종 시험은 데이터를 내보낼 수 있는지가 아니라, 사용자가 다른 환경으로 옮긴 뒤에도 자신의 맥락을 통제할 수 있는지다.

백서 4.3절

이 기준은 Still 자신에게도 적용됩니다. 여러 모델을 연결할 수 있어도 Still을 떠날 수 없다면, 모델에서는 자유로워졌어도 사용자가 자유로워졌다고 보기는 어렵습니다.

맥락은 기억이 아닙니다

근거 계약. 총람 5.1·5.3절, 개발 헌법 C5

Still은 맥락(Context)과 기억(Memory)을 구분합니다. 맥락은 작업 하나를 위해 주어지는 정보입니다. 쓸 수 있는 범위와 출처가 정해져 있고, 기한이 지나면 사라지며, 자동으로 기억이 되지 않습니다. 기억은 Still이 관리하는 기준 기록, 곧 정본입니다.

대화 전체, 모델의 추론, 검색 결과, 파일 내용은 저절로 정본 기억이 되지 않습니다. 패키지나 외부 실행기의 내부 상태도 마찬가지입니다. 제3자가 저장하려는 기억은 승인 전까지 후보(MemoryCandidate)로 남습니다.

지금의 기억 정책

근거 계약·구현. 총람 7.4절

처음에는 소유자가 직접 기억해 달라고 요청하고 확인해야 정본이 됐습니다. 그런데 실제로 써 보니, 기억할 사실이 생길 때마다 묻는 것 자체가 불편했습니다. 그래서 정책은 다음과 같이 바뀌었습니다.

표 1. 기억 정책의 변화
시기결정내용
#597명시적 요청만 정본명시적인 기억 요청과 소유자의 확인이 있어야 정본, 아니면 후보
#805 (09-28)소유자 모델 유지성공한 작업 뒤 판단 모델이 기억할 사실을 최대 5개까지 제안. 소유자가 말한 것과 추론한 것을 구분
#818, #836 (09-28)한 작업에 한 번만 묻기두 번 묻던 문제를 고치고, 내부 동작을 설명하던 문구를 없앰
#918 (10-02)묻지 않고 저장, 알리고, 되돌리기소유자 자신의 AI에 한해 바로 정본으로 저장. “기억했어요” 알림과 7일 되돌리기
#998 (10-04)자기 검토실패나 정정 뒤 놓친 것을 돌아보고 교훈 하나를 기억으로 남김

자료: 『Still 총람』 v0.1, 7.4절. 축약·재구성. 번호는 GitHub 이슈·PR입니다.

묻지 않고 바로 저장하는 방식은 소유자가 고른 AI에만 적용됩니다. 패키지 도구나 일을 넘겨받은 전문 에이전트 같은 제3자는 여전히 후보로 저장합니다. 비밀번호나 토큰처럼 보이는 값은 저장하지 않습니다.

주의 남은 위험도 기록되어 있습니다. 믿을 수 없는 웹 페이지의 문장에 속아 저장한 내용이 바로 기억이 될 수 있습니다. 지금은 출처 표시와 되돌리기로만 위험을 줄이고 있으며, 이런 공격(주입)을 막는 장치는 보류되어 있습니다.

정정, 잊기, 완전 삭제

근거 계약. 총람 7.9절

기억을 고치고 잊는 일은 관리 화면 없이 대화에서 합니다. 계약은 세 동작을 나눕니다.

정정
“그건 잘못 기억했어”처럼 대화에서 고칩니다. “틀렸다”와 “이제 맞지 않게 됐다”를 구분합니다.
잊기
바로 쓰지 않게 하고, 내용은 뺀 처리 기록만 남기며, 7일 동안 되돌릴 수 있게 한 뒤 지웁니다.
완전 삭제
되돌리기 없이 즉시 지우고, 성공·부분 성공·실패를 구분해 알립니다.

내 컴퓨터에서 잊었다고 해서 AI 공급자 쪽 사본이나 내보낸 파일, 백업까지 지워졌다고 말하지 않습니다. 이 세 동작은 계약으로 정해졌지만 구현은 아직 끝나지 않았습니다.

남은 문제

출처 총람 24장

  • 에이전트가 어떤 사실을 얼마나 확신하는지 어떻게 보여 줄지 정해지지 않았습니다. 이를 정한 표준이나 제품은 찾지 못했고, 숫자 대신 몇 단계로 나눠 보여 주자는 설계 판단까지만 와 있습니다.
  • 정정·잊기·완전 삭제 계약과, 데이터베이스 수준에서 잊는 방법에 대한 연구가 아직 서로 연결되지 않았습니다.
  • 지금의 기억 저장소에는 유효 기간과 철회 시각이 기록되지 않습니다.

다른 열린 질문은 확인된 범위와 열린 질문에 있습니다.
