Skills and expertise

A skill is a bundle of content that the AI loads to learn how to do a task. This page covers the difference between a skill format and a tradable capability, the supply-first principle, the interface decision, what the first real-use sample does and does not show, and how packages and upstream projects are handled.

Manuscripts: Whitepaper ch. 8–9, Compendium ch. 12. Last updated October 14, 2026.

A format is not a capability

Basis Hypothesis. Whitepaper ch. 8, Compendium 12.1

The public Agent Skills format bundles a SKILL.md of instructions with optional scripts, references and templates as a unit for distributing expertise and procedures. But the whitepaper distinguishes a distributable format from a tradable capability. Providing a file that describes how to do a job, maintaining it so it works in a given environment, verifying the quality of results and supporting failures are different products.

A "receipt organizing skill" name alone does not tell a buyer what they get: which inputs it handles, which tools it needs, which models and environments it was tested on, how it checks for duplicates and omissions, and who maintains it when a service changes.

The purpose of a skill economy is not to rename every service an agent but to make professional capability discoverable, delegable and verifiable.

Compendium 12.1

A skill market can also create new lock-in. Even if the file format is open, competition is limited if the required runtime, reputation, payment and access to user context are tied to one business. Not every skill needs to be a dynamically reasoning agent either; software running a stable procedure, fixed validation rules or a human-reviewed professional service may fit better. Execution evidence can be part of the grounds for confirming capability, but issuing evidence is not a quality guarantee or proof of user satisfaction.

Supply first, adapt second, learn only the gaps

Basis Contract. Compendium 12.2

On October 1 the owner said the AI should not have to rediscover a site's mechanics by trial and error every time it repeats a job. Someone may already have built a skill for it, or the service may publish one officially. The principle of the skill supply program was supply first, adapt second, learn only the gaps.

Its fourteen requirements compress this project's way of thinking. Supply comes before per-user learning. Discovery is bounded and its results are reused. Importing a skill, connecting a tool and delegating a task are different integration modes. A skill's allowed-tools marking grants nothing. Reuse methods, re-read facts. Reconcile with current state before replaying. Knowledge is not authority: sharing a public skill with family is not sharing accounts or history. A single successful trace is not automatically promoted to a trusted skill. Additions preserve existing behaviour.

The owner also asked to preserve behaviour that already worked, such as the cart, and not to compensate for a big redesign with token-hungry tests. So the program was reshaped around interface-first design and bounded verification, not a rebuild.

The interface decision

Basis Contract, Implemented. Compendium 12.3

The decision record defined a skill like this: a skill is optional, versioned knowledge carried by an existing AgentPackage, not a new executor or permission. The worker reaches the content through two effect-free host actions (skill_load and skill_resource). They are defined in one place, so the direct API, Codex and Claude Code routes all get them identically. Foreign formats are normalized once on acquisition. Rollout was staged so that, with skills off, the tool surface is byte-identical to before skills existed. Per-site strategy classes, site inheritance trees, mandatory specialist chains, translator agents and skill-specific verifiers were not adopted.

The reuse review was kept with exact revisions.

Budgets were also placed inside the existing Work budget: at most 32 descriptors and 8 KB in the catalogue, three skill loads and eight resource reads per Work, and so on. The first external supplier was one public repository pinned to a commit, accepting only folders whose licence file is Apache-2.0. Skills without a licence file were marked licence_unknown, and source-available but not open-source skills were excluded.

The risk of an AI CLI quietly showing the worker unreviewed skills from the owner's home was found and closed. Codex is passed a setting that turns off skill-instruction inclusion, and Claude Code is passed a flag that disables slash commands. This was confirmed with a real codex, a fake model and a canary skill.

Note "Implemented" means confirmed by code and unit or integration tests. It does not mean skills work well on live accounts and live services.

The first real-use sample and the scope of claims

Basis Observed, Implemented. Compendium 12.4

The skill evaluation begins by saying it is not a second test project. It maps existing evidence to the inventory, adds only the checks that were really missing, and states what remains unproven. The owner approved a live sample plan: four cases in sequence with the real Codex and a signed-in browser, changing only one product line, never paying, with caps on Works, turns, tool attempts and time, stopping at the first false completion or unrequested effect, and restoring the original state at the end.

The first run on October 3 stopped at the first case. The session was signed out, and the AI asked for sign-in at once without touching the cart. And a truthfulness bug appeared: the Work was recorded as succeeded. An answer inferring an account owner not present in the request was recorded as well.

So what can and cannot be claimed is clear.

The evidence for importing an external skill and the evidence for site-knowledge content remain two separate pieces and were not merged into one stronger claim.

AgentPackages and the distribution platform

Basis Contract. Compendium 12.5

Note This section is rules and design. Running arbitrary third-party packages and a public marketplace are not claimed as working today (see What is not claimed now).

In the long run the owner will install and replace better agents like apps. The lifecycle goes: discover, inspect and download, verify, stage, health check, install disabled, separately grant, enable and connect, run under Work-scoped Grants, update or roll back, disable or quarantine, uninstall. An update that widens authority, data destinations, memory or background behaviour, dependencies, budgets or consequential actions needs new authority. A failed update defines a path back to a known good state. Uninstalling removes the package's authority but does not delete the owner's Artifacts or retained evidence. A package's internal memory is not canonical.

Capability acquisition has a ladder from L1 to L5: manual install, recommendation, owner-approved plan, bounded standing acquisition, kernel-mediated self-request. L4 and L5 are outside the first MVP. An agent completing installation, activation or privilege escalation on its own is not the default behaviour. A recommendation is information only and never changes capability state. A model's suggestion, a catalogue entry or a bare "yes" is not an install or an approval.

Relationships with upstream projects

Basis Contract, Implemented. Compendium 12.6

As reuse grows, relationships with outside projects must be recorded precisely. The upstream relationship map separates attack surface (code installed) from actual authority (what is actually projected at runtime): neither implies the other. Relationships are classified with six terms: reference-only, vendored/patched, runtime package, protocol or schema conformance, versioned content and external service. For example, model providers are reached by implementing their wire contracts directly without an SDK, and the document names this an explicit uninspected gap. Ontology and provenance standards (OWL 2, SKOS, SHACL, PROV-O) are strictly reference-only; there is no RDF or reasoner runtime.

Dependency management adopted a single uv lock and Dependabot. Renovate could have tracked commit pins of skill content but was rejected, because changing a skill commit cannot safely refresh copied bytes, licences, digests, local wrappers and evidence of semantic impact. A bot pull request is a discovery candidate, not implementation authority. The official MCP SDK was adapted only on the host's stdio path, as an optional extra. The decision states that the 13 transitive packages the SDK brings in increase the installed attack surface, and each licence was checked.

Upstream contribution was careful too. A defect in one release of a public-suffix-list package, whose wheel and sdist bundled different list snapshots, was reproduced, and the dependency was pinned to a known good version. A draft upstream issue was prepared, but submission was left to a separate owner approval. A response-handling problem in the MCP SDK overlapped an already open upstream issue, so nothing new was submitted; instead a local adapter was kept with tests, to be removed once an upstream fix is released.
