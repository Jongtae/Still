Working with AI

In Still, the work is done by the AI the owner chose. This page explains the division of roles between the AI and Still, what must carry on when the model changes, Presence, and collaboration between people and agents.

Manuscripts: Whitepaper ch. 5–6, Compendium ch. 6, ch. 8–9 and §11.1. Last updated October 14, 2026.

The AI is the engine

Basis Contract·Implemented. Compendium ch. 6, Development Constitution C16

On September 27, 2026, it was pointed out that per-request features, such as directions, carts and particular lookups, were piling up in the code. From that realization came Development Constitution C16.

The owner’s chosen AI does the work of meeting the owner’s needs as a secretary.

Compendium §6.2
What does the work
The AI the owner chose. A subscription command-line tool (CLI) such as Codex or Claude Code, or a model connected by API, uses its tools to search, read, reason, write and act.
What the decision model does
For each request it chooses which AI tool and model to use, writes the brief (goal, relevant context, completion criteria) and hands it over, and evaluates the result. If the goal is not met, it adjusts the brief or re-delegates. It does not do the work itself, and it is not a device that mechanically applies fixed rules.
What Still code does
It directly keeps what an AI must not own: the canonical record about the owner, authority and approvals, secrets, payment and consequential-action approval, budgets, Work records and evidence, and recovery. And it removes the blockers that stop the AI tools: a login that gets stuck, a needed tool that is not exposed to the AI, wrong routing, and the like.
What it does not do
It does not build per-request features into code, and it does not branch code by site, provider, category or task name. When a request fails, it fixes the blocker or the decision model’s decision, not that one task.

An automated test (a static scan) enforces this principle too. Every proposal and change must answer: “Which AI does the work here, and is this change removing a blocker or orchestrating — or is it scripting the task?”

Note Since October 12, 2026, a Work is handed only to the current main AI while it can run. What the decision model varies is the model and the effort, not the vendor. This narrows the original idea considerably, and only the owner’s decision is on record as the basis.

What carries on when the model changes

Basis Proposal. Whitepaper §5.1, Compendium §8.1

Even when the model or the AI doing the work changes, the relationship with the same assistant that knows me should continue. What must carry on is approved preferences, current goals, and the state of the work and its basis. It does not mean every answer becomes identical.

  • It separates “which model is configured” from “which model actually ran”. A configured model is never shown as if it were the one that actually ran.
  • If switching providers changes the cost or the scope of data passed along, the user must be able to know. Automatic switching must not become a way to raise costs or widen data sharing without the user’s knowledge.
  • If a new model cannot fill a needed capability or level of quality, the difference is reported, and the options are considered: keep using the earlier model, use another means, or have the user step in.

Continuity does not hide differences in capability; it keeps those differences from costing the user their work in progress and their control.

Whitepaper §5.1

Presence

Basis Contract·Observed. Compendium §8.2–8.6, real-use study of 2026-09-23

Presence means the experience of working with one continuous, context-aware assistant that knows me, across many turns, changing tools and AIs, failures and restarts. The goal is not to pretend to be conscious or to act out emotion.

The concept came out of real-use observation on September 23, 2026. Even an ordinary request got a work-status message back, a failure sent the owner to the web management screen instead of continuing the conversation, and a follow-up request was not connected to the earlier failure. The manuscript judged the cause to be not tone but “projection”: internal concepts were leaking straight into the conversation and settings screens.

The Presence contract sets nine experience principles.

  • Conversation first, receipts on demand.
  • One assistant voice over many workers.
  • Continue before restarting.
  • Communicate meaningful progress, not scheduler state.
  • Truth before fluency.
  • Ask at the moment of need; the agent does the managing.
  • Memory is useful, scoped and correctable.
  • Proactivity must earn the interruption.
  • Model-first semantics; rules only where exactness is unavoidable.

Following these principles, Still’s settings and management happen in conversation. A separate page is used only for results that text cannot carry well, and for inputs a conversation cannot carry safely, such as secret entry, OAuth consent and payment approval.

A structure you can leave

Basis Hypothesis. Whitepaper §5.3

The more context a personal agent understands and the deeper it goes into daily life, the heavier it can become to leave that relationship. So Presence and moving memory are not opposing demands. Presence keeps the relationship going, and moving memory keeps that relationship from turning into forced dependence on one provider.

A good personal agent should give reasons to use it for a long time, but must not make the user unable to leave because they used it for a long time.

Whitepaper §5.3

Collaboration between people and agents

Basis Proposal. Whitepaper ch. 6, Compendium ch. 9

The whitepaper proposes evaluating autonomy (finishing without human intervention) and collaboration (continuing while reflecting the human’s intent when they step in midway) as different axes.

For example, the user first puts a book in a cart. The agent suggests other books based on interests and a budget the user has allowed. When the user removes one or changes an edition, the agent respects the change. Items not yet decided are held and picked up again in the next conversation. The purchase itself happens within a delegation given in advance or through a separate confirmation step.

For that, collaboration has to be designed around the whole Work, not a single tool call. The whitepaper proposes handling the object, current state, change history, actor, delegation scope and completion evidence together. If the agent tries to increase a quantity based on its earlier plan while the user is removing that product, it does not apply the stale plan; it checks the state again and then adjusts the plan.

Note A delegation to add to a cart never grows into a delegation to pay. The shape of answer the compendium sets as a target is: “I added one copy of the book you asked for to the cart at the bookstore you named. I did not order or pay.”

Field record

Basis Observed. Real-use recording, October 2026

In a real Telegram conversation, a single command switched the AI doing the work from Codex to Claude Code. When the owner then said only “Not Jardin, something pricier for a change,” Claude Code remembered the Momos coffee beans it had recommended earlier for lattes and suggested them instead. This is an edited real-use recording, not the result of validating a particular version from start to finish. The recording can be seen on the Still home page.

Remaining problems

Source Compendium §8.8, 9.4, 22.2

  • An owner’s correction made mid-work reaches the AI that is doing the work but not the decision model. So a re-delegation plan can be made without knowing about that correction.
  • Presence’s acceptance scenarios are tested automatically with premade fake data (fixtures). There is a report that six checks made on real Telegram on September 25, 2026 did not behave as the tests predicted, and the cause is still unknown.
  • The decision model actually running on the owner’s accounts has not been observed yet.
