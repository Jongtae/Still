Authority, connections and evidence

This page explains the protection rules Still enforces today, the kinds of action, the order in which it looks for a needed capability, and the difference between saying "done" and having proof it was done.

Manuscripts: Whitepaper ch. 7 and 9, Compendium ch. 10–11. Last updated October 14, 2026.

The protection rules enforced today

Basis Contract and implemented. Compendium 10.1–10.2

This is a pilot: one owner, using their own machine and their own accounts. In this phase two rules are enforced on every request.

  • Secrets never enter a model prompt, a log or Evidence.
  • Each payment needs the owner's approval.

Folder grants, owner scope, secrets, per-action payment approval, no replay of the same action and authority over memory also stay as they were. What was removed: per-request judgments about whether information is sensitive, re-asking about ordinary search terms, and per-provider blocks. These were deferred to a separately started hardening program.

Instead, each Work leaves an information-use audit. It shows which owner information (profile, memory, calendar, files, current context, conversation) was used, which AI, route and model it went to, and which queries a web search used if one ran.

Note An audit tells you what happened; it does not prevent it. The proposal for injection and exfiltration defences against the combination of private data, internet access and autonomous action was parked by owner decision on September 28, 2026.

Kinds of action

Basis Contract and implemented. Compendium 10.3

Reading public information, changing a cart or a hold, entering identity details, confirming a reservation, sending a message and paying are different kinds of action, even when a website handles them in one flow. A request to look something up does not grant cart or payment authority. If the request or the authority changes, an earlier approval that no longer covers the change cannot be used.

Payment protection does not rely on the model's judgment. Typing into a card number, CVC or OTP field always needs owner approval, whatever the model calls the action. The model's own label for an action and an MCP server's "read-only" hint are treated as hints only. Such a label can add a requirement, but never remove one.

The order for finding a capability

Basis Contract and implemented. Compendium 11.2

When a Work needs a capability it lacks, code does not decide in advance, task by task, which service to use. The contract sets only the order of places the AI looks.

  1. AI ecosystem capabilities: connectors, MCP servers and plugins already present, or the official MCP Registry and vendor directories.
  2. The service's own developer documentation and API, and maintained public implementations.
  3. Skills: public skills first, then Still reference skills. A skill says "how to do it"; it is never authority.
  4. Generic channels: a signed-in browser, API reads that use a secret slot, sandboxed code runs.
  5. Building something new, only for a concrete unmet contract after a review of existing solutions.

This order is the default when other things are equal. In practice the choice also weighs the owner's install and registration burden, whether a route is official, standard and maintained, whether it matches the scope needed, how secrets are handled and how reliable it is. The capability search stage only finds information; it installs, connects and signs in to nothing.

Words and proof

Basis Proposal. Whitepaper 7.1

Suppose an agent said "done" and the result is not there. The agent may not have sent the request. The service may have received it without applying it. It may have been applied and then changed again. What is needed is not an agent that remembers confidently but evidence that separates request, processing, observation and later change.

Table 1. Kinds of record and what they can check
Kind of recordWhat it checksWhat it cannot settle alone
Execution request recordWhich actor submitted which requestWhether the request was actually applied
Observation recordWhat screen or response was seen at a given timeThe service's full internal processing and change history
Service processing receiptWhat the service confirmed it did with which requestIssuer error or falsehood; the current state afterwards
Ledger inclusion proofWhether a record was included in a verifiable structureTruth of the content; whether every event was recorded

Source: Whose Agent? (Korean) v0.3.1, section 7.1. Table reproduced.

This table is not a ranking from weak to strong evidence; it separates evidence that answers different questions.

Digital signatures do not remove these boundaries either. The W3C Verifiable Credentials data model also states that verifiability does not mean the claims inside are true.

Example: a cart record

Basis Proposal. Whitepaper 7.2

Note This is a design case that assumes a store provides processing receipts and change history. It does not mean any particular store, or Still today, supports this.

  1. 10:00. Still submits request R1 to add milk. The store issues a processing receipt, with the request number, saying the cart moved from version 41 to 42.
  2. 11:00. A request R2 to remove the milk is submitted from the mobile app on the same account. The store leaves a separate receipt saying the cart moved from version 42 to 43.
  3. 13:00. The user asks why the milk is not there. Still checks the two receipts and the state at the time of the lookup, then answers.

According to the service's records, the 10:00 request to add it was applied, and a removal submitted from this account's mobile app at 11:00 was applied. A check at 13:00 shows there is no milk.

Example answer, Whitepaper 7.2

This explanation is different from "I think I added it". It also does not assert "you deleted it yourself", because the records identify the account and the client path, not the person who actually acted.

That a past action succeeded is different from its result still holding now. An authenticated account, a client, a delegated agent and an actual person must not be treated as the same actor.

Whitepaper 7.2

Ledgers and signatures

Basis Proposal. Whitepaper 7.3–7.4

  • Missing records matter as much as altered ones. If Still records only its own requests and not the user's app actions, it cannot explain how things changed. Every path that changes the same object must leave a common processing and change record.
  • So the whitepaper proposes that the service that actually changes the state be responsible for producing the evidence along with the change, rather than having an agent write a record after it has worked.
  • A blockchain is one option for preserving evidence, not a device that creates facts. Writing to a ledger does not check whether the content is true.
  • Verifiable record structures exist, such as Certificate Transparency (RFC 9162) and the SCITT architecture (RFC 9943), but proof of registration does not guarantee that the content is true or that everything was recorded.

Portable execution evidence

Basis Proposal. Whitepaper 7.5

When changing agents, users should be able to take, as far as needed, not only preferences and conversations but the processing evidence for the work being handed over. The new agent should not accept the previous agent's summary as fact but re-check it against preserved originals and issuer information. Moving evidence does not create new authority to act. Verifiability does not mean publishing every record either.

A trustworthy agent ecosystem is not one that assumes every participant is always right. It is one in which the remaining evidence can still be compared when participants are wrong, lose their memory or are replaced.

Whitepaper 7.6

The repository's truthfulness rules

Basis Contract, implemented and observed. Compendium 10.8

What Still can do internally, without cooperation from outside services, is already set as rules.

  • Progress and action receipts are built only from observed Work and tool events. Requested, observed, failed and unknown are kept distinct.
  • The effect of an action on an outside service is recorded as none, confirmed or unknown. An action whose result is unknown says so, and the same action is never silently re-run.
  • No invented ETA, tool execution, model identity or successful external effect.
  • Nothing is called "delivered" without an unambiguous confirmation that the other service received it.

These rules actually caught a bug. In the skill evaluation of October 3, 2026, the AI saw that the owner's store session was signed out, asked for sign-in without touching the cart, and honestly answered that nothing was added. Yet the Work was recorded as a success although it was waiting for a sign-in. That defect is left as a separate follow-up.

Connection and independence

Basis Hypothesis. Whitepaper ch. 9

MCP covers how AI applications exchange with external tools and data, and A2A covers communication and collaboration between agents on different systems. The whitepaper does not aim to replace these protocols. Its question is who chooses what can be connected, who manages personal context and authority among those connections, and how the user can change the whole environment.

The product meaning of interoperability lies not only in a longer list of connections but in the user being able to form, adjust and end relationships.
